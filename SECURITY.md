# Security Policy - Ollama Phone Chat

## Security Philosophy
Ollama Phone Chat is built on a "Local-First" architecture. By default, it operates over your Local Area Network (LAN). While this provides a layer of physical security, users should be aware of the security considerations when using and potentially exposing this service.

---

## Security Features

### 1. HTML Sanitization
We use [DOMPurify](https://github.com/cure53/dompurify) on the frontend to sanitize all Markdown output before it is rendered, and chat titles/user messages are inserted with `textContent`. This prevents Cross-Site Scripting (XSS) attacks from malicious or malformed model responses or stored history. `marked` and `DOMPurify` are vendored under `public/vendor/` (no CDN), with licenses and checksums in [THIRD_PARTY_NOTICES.md](./THIRD_PARTY_NOTICES.md).

### 2. SQL Injection Prevention
All interactions with the SQLite database use **parameterized queries** via the `sqlite3` driver. This ensures that user input cannot be used to manipulate database queries.

### 3. Static File Isolation
The Express server is configured to serve static assets only from the `public/` directory, preventing directory traversal attacks.

### 4. Transparent Data Encryption (TDE)
When an `APP_PASSWORD` is configured in the environment, the application encrypts `message.content`, `message.thinking`, and `chat.title` before persistence.
- **Algorithm**: AES-256-GCM (authenticated encryption)
- **Key Derivation**: scrypt with a random 32-byte per-install salt (`data/.key_salt`)
- **IV / Tag**: random 12-byte IV and 16-byte authentication tag stored per record
- **Legacy data**: AES-256-CBC rows from v0.0.4 are decrypted on read for backward compatibility; new rows always use GCM.
- **No password**: history is stored unencrypted. This is intentional and matches the documented behaviour.
- **Password changes**: changing `APP_PASSWORD` makes existing ciphertext unreadable. Back up the database before rotating the password.

### 5. App-Level Authentication
If an `APP_PASSWORD` is set, the server enforces a custom header check (`X-App-Password`) for all API requests. The frontend provides a secure login overlay to handle this locally.

### 6. Content Security Policy
Every response includes a restrictive `Content-Security-Policy`:
- `script-src 'self'` — no inline handlers and no third-party scripts.
- `object-src 'none'`, `base-uri 'none'`, `form-action 'self'`, `frame-ancestors 'none'`.
- `connect-src 'self'` — the page only talks to the bridge.
- `img-src 'self' data: blob:` — remote images in model output are blocked, so the page does not leak requests to third parties.
- `style-src 'self' 'unsafe-inline'` is required by the existing inline `style` attributes in `index.html`.

Additional headers: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, and a `Permissions-Policy` that disables camera, microphone, and geolocation. `x-powered-by` is disabled.

## Security Recommendations

### LAN Security
Since the application runs over HTTP on your LAN, anyone on the same Wi-Fi could potentially access the bridge if they know the IP and port. We recommend:
-   Running the server only on trusted networks.
-   Stopping the server when not in use.

### Remote Access (Public Internet)
If you choose to expose Ollama Phone Chat to the public internet (e.g., via NGROK, Cloudflare Tunnels, or Port Forwarding), you **MUST**:
1.  **Use HTTPS**: Ensure the connection is encrypted.
2.  **Implement Authentication**: The current version does not include built-in user authentication. Use a reverse proxy (like Nginx or Caddy) to add Basic Auth or OIDC if exposing to the web.
3.  **Secure your `.env`**: Never commit your `.env` file containing API keys to public repositories.

If you discover a security vulnerability within this project, please **do not open a public issue**. Instead, report it privately to the maintainer:

-   **Lead Maintainer**: Krishna Kanth B

## Warning: LLM Hallucinations
Please remember that the responses generated by the models are provided by your local Ollama instance. Ollama Phone Chat is a bridge and does not control the content or safety of the model's output. Use "thinking" models or system prompts to guide model behavior safely.
